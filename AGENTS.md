# AGENTS.md: edx-platform (fccn/edx-platform, the NAU fork of openedx-platform)

Guidance for coding agents and for people working in this repository.

## What this is

The NAU fork of [openedx/openedx-platform](https://github.com/openedx/openedx-platform) (LMS and Studio/CMS). The
NAU branch for each Open edX release is `nau/<release>.master`. The current one is the default branch
(`nau/teak.master`). The older branches (`nau/redwood.master`, `nau/quince.master`, …) are history: do not change
them unless asked.

The upstream `README.rst`, `docs/` and the upstream contribution rules still apply. This file only adds what is
specific to NAU.

## Where a change belongs

1. **Prefer [fccn/nau-openedx-extensions](https://github.com/fccn/nau-openedx-extensions)**: a Django plugin,
   an Open edX filter or signal, a setting or a template override. Code there survives an Open edX upgrade.
2. **Prefer upstream** for a bug that is not NAU-specific: fix it upstream, then backport the merged fix here.
3. Patch this fork only when neither is possible. Keep the patch small and self-contained, so that it can be
   re-applied on the next release, and say in the pull request why it cannot live in the extensions.

## Backports and NAU commits

- A backport from upstream is **one commit per upstream commit**, cherry-picked with `git cherry-pick -x` so that the
  original hash is recorded. Keep the upstream message and add `(backport)` and the **full URL** of the upstream pull
  request: the `(#1234)` in an upstream message links to the wrong pull request in this fork. Do not squash several
  backports together.
- A NAU patch is one self-contained commit that follows the shared conventions below, so that it can be
  cherry-picked onto the next `nau/<release>.master`.
- Do not reformat or "clean up" upstream code: every changed line is a possible conflict on the next upgrade.

## Running and testing

There is no standalone setup: run the platform through
[fccn/nau-tutor-configs](https://github.com/fccn/nau-tutor-configs). Its README, section "Developing into
openedx-platform", mounts this clone into the dev containers (`make mount-openedx-platform`,
`make build-openedx-dev`, `bin/tutor dev start -d`). Run the tests inside the LMS or CMS container, limited to
the modules you changed, for example:

```bash
bin/tutor dev run lms bash        # then, inside the container:
pytest lms/djangoapps/<app>/tests/test_<module>.py
```

The upstream GitHub workflows (unit tests, quality, pylint, migrations, …) run on pull requests. Read their
results. A failure in code you did not touch can be a pre-existing one from upstream: say so in the pull request
instead of "fixing" it.

## Rules for this repository

- A new migration in the fork is a cost on every upgrade: avoid it, or put the model in nau-openedx-extensions.
- After a merge, the change only reaches an environment once nau-tutor-configs builds a new image with the new
  commit, and that image is deployed through nau-kubernetes-manifests.

## NAU conventions (shared by every NAU repository)

NAU is the Open edX platform run by FCCN. Work is tracked in issues of
[fccn/nau-technical](https://github.com/fccn/nau-technical/issues), which also holds the cross-repository
documentation in `docs/` (start at `docs/overview.md`; the full list of repositories is `docs/repositories.md`).

### Commits

- Use [Conventional Commits](https://open-edx-proposals.readthedocs.io/en/latest/oep-0051-bp-conventional-commits.html)
  (OEP-51), unless the repository section above says otherwise. Most repositories enforce them with the shared
  Open edX commitlint workflow on every pull request.
- Allowed types: `feat`, `fix`, `perf`, `refactor`, `docs`, `test`, `build`, `style`, `chore`, `revert`, `temp`.
  There is **no `ci` type**: use `build:` (or `fix(ci):`) for CI changes. Mark breaking changes with `!` (`feat!:`).
- Header: at most 110 characters, imperative mood, lowercase after the colon: `fix: keep the session fresh in the CMS`,
  not `Fixed session` or `fixes session`.
- Scope is optional, unless the repository section above defines one, for example the environment in the
  Kubernetes manifests.
- The body says **why**: the problem, its cause, and what the change affects. The commit message is what stays in
  the history; the pull request description does not.
- End every commit message with the issue it belongs to:

  ```
  Related to: fccn/nau-technical#<issue-number>
  ```

  Use `fccn/<repo>#<number>` when the issue lives in another repository. Use this exact form. Do not use `Refs`,
  `refs:` or `fixes`, and do not use a bare `#123`. **Never invent an issue number**: if you do not know it, ask.
- Do not add AI attribution (`Co-authored-by` for an AI tool, "generated by …") to commits, pull requests or issues.
- Commit with the developer's own git identity. Never run `git config user.name` or `git config user.email` in a
  repository or worktree.
- Never bypass hooks with `--no-verify`.

### Pull requests

- Every change goes through a pull request, documentation and one-line fixes included. Never commit or push to the
  default branch. The default branch differs between repositories (`main`, `master`, `nau/teak.master`, …): check it
  with `git symbolic-ref refs/remotes/origin/HEAD`.
- Branch name: `<github-user>/issues/<issue-number>/<type>-<short-description>`, for example
  `jdoe/issues/1042/fix-vrrp-interface`.
- **Small and focused**: one feature or fix per pull request, so that it can be reviewed well. Leave out unrelated
  refactors, reformatting and dependency bumps. Put a mechanical change (a rename, formatting) in its own commit or
  pull request, so that the logic change stays easy to read.
- When a change cannot be small (an Open edX or Richie upgrade, a large migration, a big generated diff), say so at
  the top of the description, and why. Tell the reviewer where to start and which files are generated or mechanical.
  If the work can be delivered in steps that each leave the default branch working, open one pull request per step.
- A change that needs several repositories is one pull request per repository. Link them to each other by full URL,
  and give the merge order in the description.
- The title follows the commit header format (with one commit, it is that commit's header). The description says
  **what** changed and **why**, **how it was tested** and what the reviewer should look at. It ends with:

  ```
  Related to:
  - fccn/nau-technical#<issue-number>
  ```

- In a pull request, an issue or a commit message, link another pull request, issue, commit or document by its
  **full URL**. GitHub turns a short `#123` into a link to the wrong repository.
- Run the checks listed in the repository section above before you push. CI must be green before you ask for review.

### History: squash right before merging

NAU repositories merge pull requests with **Rebase and merge**: the commits of the branch land on the default branch
as they are, with no merge commit. The goal is a history in which each commit is one complete feature or fix with a
message that explains it, so that it can be read, reviewed, reverted and backported (`git cherry-pick`) on its own.
`git log --grep='nau-technical#<issue-number>'` finds the commits of an issue.

- **During review, add commits.** Push each round of changes as new commits on top of the branch, so that the reviewer
  sees what changed since the last round. Do not squash, rebase or force-push until the review is done. If you need
  the latest default branch, merge it in: the squash removes the merge commit.
- Review commits still need a valid header, because commitlint checks every commit of the pull request:
  `fix: address review comments` or `style: fix lint` pass, `address review comments` does not. When you commit a
  suggestion on GitHub, replace its default message ("Apply suggestions from code review").
- **Right before merging, squash** the commits into the real features or fixes of the pull request, usually one. Use
  several commits only for changes that are clearer apart, for example the refactor a fix needs, then the fix. Each
  final commit builds and passes the tests on its own, contains the files it regenerates, and has its final message:
  header, why, trailer. If other people wrote commits in the pull request, credit them with a
  `Co-authored-by: Name <email>` line. Start with no uncommitted changes.

  One feature or fix, the usual case:

  ```bash
  git fetch origin
  git reset --soft "$(git merge-base HEAD origin/<default-branch>)"   # remove the commits, keep their changes
  git commit                                                          # one commit, with the final message
  git diff --quiet ORIG_HEAD HEAD && echo "content unchanged"         # must print it
  git push --force-with-lease --force-if-includes
  ```

  Several features or fixes: replace the `reset` and the `commit` with
  `git rebase -i "$(git merge-base HEAD origin/<default-branch>)"`. In the list it opens, move each review commit
  under the commit it belongs to and change its `pick` to `fixup`. Change `pick` to `reword` to rewrite a message.
  Then check and push the same way.
- The "Compare" link of that force-push on GitHub shows no change: that is how the reviewer checks that the squash
  changed the commits, not the code. Merge with **Rebase and merge** once CI passes. If GitHub reports conflicts,
  rebase on the latest default branch (`git rebase origin/<default-branch>`), push again, and ask the reviewer to look
  at the result.
- Force-push only your own pull request branch, and only with `--force-with-lease --force-if-includes`. After a
  `git fetch`, `--force-with-lease` alone overwrites commits someone else pushed to the branch. Never force-push a
  default or release branch, or someone else's branch.
- Stacked pull requests (one based on another): squash and merge the lower one first. Then move the next one onto the
  default branch with `git rebase --onto origin/<default-branch> <old-tip> <branch>`, where `<old-tip>` is the last
  commit of the lower pull request in your branch (`git log --oneline` shows it just below your own commits).
  Otherwise the lower pull request's commits, from before its squash, land a second time.
- Agents: do not squash or merge unless asked. The developer decides when the review is done.

### Reviewing pull requests

- Review the change against the rest of the codebase, not just the diff: callers, tests, settings, migrations,
  and the other repositories it touches.
- Verify claims yourself (run the code or the tests, read the source) instead of writing "this needs checking".
- Review each round through its new commits: they show what changed since your last review.
- Whoever merges checks the final commits first: they land as they are, so each one must make sense on its own and
  have its final message. The "Compare" link of the squash push must show no change in content.
- Do not repeat a comment another reviewer already made: react to it or reply "agree" and look for new problems.
- Every assigned reviewer re-checks the fix before approving, not just the one who found the problem.
- Agents: do not post comments, reviews or approvals on GitHub unless explicitly asked. Give the review to the
  developer instead.

### Safety

- **Secrets**: never print, log, commit or paste into an issue or PR a password, token, private key or the content of
  `secure-nau-data`. Redact secrets in any output you show. If you find a secret committed somewhere, report it.
- **Environments**: dev → stage → production. Changes reach production last and only after they have been seen
  working on stage.
- Do not run anything that changes a real environment unless the developer explicitly asks for it. That includes
  deploys, `ansible-playbook` without `--check`, `kubectl apply/delete/edit`, ArgoCD syncs, database writes and
  restarts. Read-only inspection is fine.
- Do not edit generated files. Change the source (templates, `config.yml`, `.in` requirement files, …) and
  regenerate.

### Working style

- Do not assume facts about this project that are not written in this repository or in nau-technical: domain
  names, hosts, environments, owners, release dates. Ask.
- Make the smallest change that solves the problem. Follow the style of the surrounding code and the repository's
  linters. Do not reformat code you are not changing.
- Add or update tests together with the code they cover.
- User-facing text goes through translations (the platform language is Portuguese, PT-PT). Code, comments, commit
  messages, pull requests and technical documentation are in English.
- When behaviour, setup or operations change, update the README of the repository and, if relevant, the matching
  page in nau-technical `docs/` in the same pull request or in a linked one.
- Pin versions as the repository already does (lock files, `requirements/*.txt`, git hashes). Explain every new
  dependency in the pull request.
